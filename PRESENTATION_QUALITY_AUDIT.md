# Ledify presentation pipeline audit

**Updated:** The subsequent [presentation system corrections](PRESENTATION_SYSTEM_CORRECTIONS.md) supersede this audit's visual-description behavior, subtitle handling, response duplication and PDF/PNG renderer notes.

## Findings and changes

| Root cause | Resulting change |
| --- | --- |
| Renderers read legacy keys instead of canonical `titleContent`, `sectionContent`, `textContent`, `summary`, `conclusion`, and case-study `action` | The production registry uses one canonical renderer covering all 22 semantic slide types. Every supplied visible field is rendered; metadata such as IDs and search queries stays internal. |
| Layouts sliced arrays, and unknown layouts produced fallback content | Production rendering neither slices content nor creates placeholder slides. Unsupported structures and excessive density produce slide/field diagnostics. |
| Meaningful-item counting could accept multiple headings without descriptions | Lists, cards, processes, timelines and roadmaps require meaningful descriptions; focused explanations require a body. |
| Theme body sizes commonly started at 16 pt, with individual layouts using smaller text and inconsistent geometry | Consistent 0.72-inch margins, 34 pt titles, 40 pt covers, 20–24 pt body text, restrained accents, editable shapes/text, and contrast correction. Relationship captions/chart labels can use 18 pt; page numbers use 12 pt. |
| Count handling had no default 8–10 policy, and outline/schema/validator limits differed | One resolved count policy governs the outline and its strict schema. Content generation iterates that exact outline; normalization, rendering metadata and preview checks retain the same count. Collection capacities are shared by schema, validator and renderer. |
| URL extraction flattened the whole page and could wait indefinitely | A 20-second fetch timeout, HTTP/HTTPS validation, preference for article/main content, boilerplate removal, and paragraph boundaries. |
| Final file/URL numerical validation used an undefined `sourceNumbers` variable | The source-number set is initialized; regression tests cover supplied and unsupported numbers for both input types. A real URL run exposed this defect. |
| PDF extraction and image conversion initialized incompatible native canvas classes in one process | PNG conversion runs in an isolated, bounded worker, with failing-page diagnostics and clean termination. |
| LibreOffice's shared profile could cause conversion timeouts | Each conversion uses an isolated profile. PDF/PNG failures retain successfully generated artifacts and return explicit partial-success status. |
| Startup printed the database connection URI; file failures logged raw errors | Removed URI logging and reduced file-failure logs to diagnostic identifiers. AI logs contain stage/model/usage metadata rather than source text or full model responses. |

## Count precedence and API use

1. Top-level request `slideCount` wins.
2. Otherwise `context.slideCount` wins.
3. Otherwise a count in the text prompt or `context.keyInstructions` is used. Examples include `five slides`, `9-slide presentation`, and `slide count: 12`.
4. Otherwise the outline chooses 8–10 slides for the material.

Counts include the title and ending. The current supported generation range is **1–12**, inherited from the structured-generation schema; it is an application limit, not a PowerPoint file-format limit. A one-slide request is an opening/overview. Larger decks return `INVALID_SLIDE_COUNT` with the supported range and guidance to split the request. Conflicting natural-language counts require an explicit field. URL/PDF source text itself is not interpreted as a user instruction to change the count.

```json
{
  "textPrompt": "Explain the supplied report in five slides.",
  "outputType": "presentation",
  "slideCount": 9,
  "context": { "audience": "Managers" }
}
```

This generates exactly **9 total slides**. The same top-level field works for URL requests and multipart file uploads. Multipart `context` remains serialized JSON; numeric strings such as `"9"` are accepted for `slideCount`. Invalid counts/context return HTTP 400 without an AI call. Existing successful HTTP envelopes and preview/download fields remain.

Programmatic callers pass `{ slideCount: 9 }` as the fourth `generateService` argument.

## Rendering and repair

`professionalLayouts.mjs` owns the common composition rules and canonical type branches; `contentFit.mjs` rejects text that exceeds a conservative wrapping estimate at the chosen readable size. The AI runs the same composition checks before accepting each slide. A failed field receives a targeted retry with a concrete character budget. There are at most three attempts per outline/slide, and already completed slides are not regenerated by that retry.

There is no clipping, ellipsis, array slicing, font shrinking, invented chart data, or fallback slide in this production renderer. Dense content is rewritten by the model within the requested count or returned as a clear failure. The shared capacities allow up to six list/card/process entries, three comparison alternatives, five relationship nodes/links, four statistics, eight chart categories/three series, and four table columns/six rows. Actual text must also fit.

Charts remain native editable PowerPoint charts. Tables use editable text and cells. The existing visual-description contract provides no actual image asset, so text-visual slides display an editable concept description alongside the explanatory text; image retrieval/generation was not added.

## Practical limits

The tests used the configured Gemini credentials, Node 24.14.0 and installed LibreOffice. Set `GEMINI_API_KEY` and optionally `LIBREOFFICE_PATH`; start from the repository root so artifact paths resolve correctly. Install the current lockfile with `npm ci`; this repository currently places some server runtime packages in `devDependencies`, so an install omitting them will not start the server.

MongoDB-backed successful POST generation/persistence was **not** exercised. Service generation, extraction, conversions, controller validation and artifact HTTP routes were exercised separately. The URL test used a real local HTTP article; authenticated sites, JavaScript-only pages and arbitrary public-site extraction were not validated. Scanned PDFs require OCR before upload.

Text fit uses a conservative estimate, not PowerPoint's own font-shaping engine. Custom fonts, CJK/RTL text and native Microsoft PowerPoint rendering were not visually validated. Review custom-font exports in the target viewer.

Source grounding is not a universal fact checker. It catches unsupported quantitative chart/statistic values and several numerical/source errors, but cannot prove arbitrary paraphrases or relationships. Editorial review remains necessary: the original generated content included oversimplified summaries and imprecise relationship labels. The delivered samples received 17 explicit source/editorial corrections after review, were rendered again, and retain the original generated content for comparison. These sample corrections are not an automatic product feature. Prompts now explicitly preserve actors, causal relationships and conditional language, but universal factual correctness is not claimed.

Generated files and isolated LibreOffice profiles have no automatic retention policy. Long requests remain synchronous; larger deployments should use job processing and a retention policy. Document/webpage rendering was outside this presentation-focused change.
